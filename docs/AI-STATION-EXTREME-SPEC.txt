 01. Executive Summary and Hard Constraints
 AI Station is a fictional survival-management game about operating a remote autonomous ocean station. The station itself is the AI.
 There is no human crew-management loop and no need for living quarters. The player sets priorities, maintains systems, develops
 resource chains, researches improvements, and sends an autonomous submarine deeper into the ocean.

 Must preserve
 • Portrait-friendly 2D side view: station at top, clear ocean surface, open underwater descent below.

 • Station is one coherent cutaway facility with continuous hull, floors, rooms, bulkheads, corridors, machinery footprints, pipes, cables,
 platforms, ladders, hatches, and plausible access.

 • Underwater center stays mostly open for the sub. Fixed cliff/reef edges, occasional ledges, fish, wreck silhouettes, coral, and deposits
 provide context without cluttering the travel lane.

 • Looping vertical background uses reusable tiles and parallax: distant silhouettes, midground ruins, foreground cliffs.

 • One small autonomous submarine with tiny articulated arms scans, grabs, and mines resource nodes on cliff faces and seabed.

 • Depth has real consequences: pressure rises; hull rating, battery, tools, cargo, power, and upgrades affect mission reach and safety.

 • Organic material can be captured and processed into bio-nutrients or industrial inputs. The sub collects minerals, salvage, and unusual
 samples. Refining converts inputs into fuel/oil, components, and upgrades.

 • Selecting a module/resource opens an inspection panel with status, condition, inputs/outputs, power, work, faults, and actions.

 • Do not add human crew, living quarters, combat, online multiplayer, top-down ocean map, photorealism, or a 3D redesign.

 02. Vision, Player Role, Objectives, and Core Loop
 Player role
 The player is the operator and strategic partner to the station AI. The station is the persistent base and main character-like entity. The
 player sets priorities, configures machines, purchases upgrades, sends the submarine on missions, and responds to warnings. The
 intended feeling is tending a living industrial organism, not clicking disconnected menus.

 Core loop
 1. Observe power, inventories, machine queues, station condition, alerts, and sub status.

 2. Identify the bottleneck: power, storage, organic input, processing, research, repair, or exploration.

 3. Set operating priorities or configure the next sub mission.

 4. Advance simulation time; machines consume inputs, produce outputs, wear, and pause when blocked.

 5. Sub travels, scans, mines/captures, manages battery/cargo/hull, and returns when safety rules trigger.

 6. Unload cargo into finite storage; processing/refining convert materials into useful products.

 7. Spend resources on repairs, modules, upgrades, and research.

 8. Unlock deeper zones and harder deposits; repeat with more capability and risk.

 Objectives and failure philosophy
 • Short-term: keep power/storage stable, complete a safe mission, prevent a critical module failure.

 • Mid-term: establish resource chains and upgrade hull, battery, tools, cargo, and sensors.

 • Long-term: exploit rare deposits, expand capability, automate routine decisions, sustain operations at depth.

 • Warnings precede most serious failures. Alerts explain cause, consequence, and response.

 04. Coordinates, Simulation Clock, and Update Order
 Units
 Use one consistent internal unit set: distance meters, time seconds, energy kWh, power kW, mass kg or configured resource units,
 temperature °C, pressure kPa, condition 0–100%. Do not mix rates and totals. Round for display only.

 Simulation clock
 Rendering and simulation are separate. Recommended fixed simulation step ∆t = 1 simulated second. Rendering may run at 30–60
 FPS. Pause freezes simulation timers while UI remains interactive. A speed multiplier scales simulation advancement uniformly.

 Update order each tick
 1. Apply queued player commands; validate costs and requirements.

 2. Calculate generation, battery charge/discharge, and power allocation.

 3. Resolve transfers and reserve inputs for machine jobs.

 4. Advance processing, refining, capture, research, repairs, and construction.

 5. Advance sub movement, depth, pressure, tool use, battery, cargo, and navigation.

 6. Update world nodes, depletion, fish populations, and hazards.

 7. Apply condition wear, heat, faults, and failure checks.

 8. Recompute inventory/capacity, alerts, unlocks, and derived status.

 9. Publish authoritative state and save at configured checkpoints.

 Core formulas
 attempted_quantity = rate_per_second * delta_seconds

 actual_output = min(attempted_quantity * efficiency, input_limit, power_limit, free_output_capacity)

 condition_factor = clamp(condition / 100, minimum_efficiency, 1.0)

 effective_rate = base_rate * condition_factor * upgrade_multiplier * operating_modifier

 For a simple prototype, minimum_efficiency may be 0.25 until condition reaches zero, at which point the machine is disabled. All values
 are configurable. Never allow negative inventory or condition.

 Pause/speed
 • Pause freezes all simulation systems, not just visible animation.

 • Normal = 1×; optional fast modes = 2× or 4× using the same simulation clock.

 • Optional pause-on-critical setting is explicit; do not unexpectedly alter pause state.

 • Changing speed must not complete jobs twice or break accounting.

 Common operating rules
 • Reserve inputs at job start or consume continuously; choose one policy consistently.

 • If output cannot be stored, pause before consuming more input unless recipe explicitly has a buffer.

 • Insufficient power follows one documented policy: proportional rate reduction or stop. Show granted power and reason.

 • Wear increases from active work/stress, not just being switched off.

 • Inspection shows status, condition, current job, inputs/outputs, power, faults, upgrades, actions.

 • Every action validates conditions before spending resources. Failed purchase has zero cost.

 06. Station Modules and Machine Behavior
 6.1 AI Core
 Central controller; not a resource generator. Maintains module state, evaluates warnings, runs user-defined priority rules, coordinates
 automation, and records diagnostics.

 • Inputs: power, sensors, configuration. Outputs: control decisions, alerts, mission recommendations.

 • Upgrades: more automation rules, diagnostics, sensor range, coordination efficiency.

 • Failure: automation becomes limited/delayed; preserve manual controls where possible.

 • UI: overall status, alerts, module list, automation policy editor.

 6.2 Generator
 power_generated = rated_power * condition_factor * fuel_factor * upgrade_multiplier

 • Output never exceeds rated/safe output.

 • Fuel-based generator consumes configured fuel per energy unit; other generator types need explicit sources/modifiers.

 • High load increases heat/wear. Overload can create faults.

 • Upgrades affect output, efficiency, reliability, fuel capacity, overload tolerance.

 • Failure lowers power budget and raises a high-priority alert.

 6.3 Power distribution
 Treat distribution as a logical network. Every powered module requests a rate; the allocator grants power by stable priority. Suggested
 tiers: 0 = Core/emergency sensors; 1 = sub safety/dock; 2 = processing/refining; 3 = research/optional utilities.
 available_power = generation + battery_discharge - required_reserve

 grant_i = min(request_i, remaining_power_for_priority_tier)

 Within a tier, use proportional allocation or stable module-ID order. Pick one and expose it in settings. When demand exceeds supply,
 lower-priority systems slow or pause. Show generated, requested, granted, and reserve power.

 6.4 Storage
 • Finite capacity measured in mass or volume; choose one authoritative rule.

 • Separate classes: bins for solids, tanks for fluids, sealed cases for samples, chilled bins for perishable organics.

 • Transfer limited by source amount, destination capacity, and transfer rate.

 • Overflow pauses incoming transfers and shows warning; never delete resources silently.

 • Optional spoilage only for configured perishable resources with explicit decay/byproduct rules.
 transfer = min(requested, source_available, destination_free_capacity, transfer_rate * delta_seconds)

 6.5 Organic capture/intake
 • Receives fish, biomass, and other organics from a real configured source or sub cargo.

 • Inputs: delivered organics; power for sorting/pumping. Outputs: sorted biomass, samples, waste, feedstock.

 • Rate limited by equipment, input, power, and storage.

 • Optional ecology: overharvest reduces local fish availability; recovery uses defined regeneration.

 • Upgrades improve capture efficiency, sorting, throughput, or sustainable yield.

 6.8 Research lab
 • Research is a timed queue with explicit cost, duration, prerequisites, and effect.

 • Validate costs before start. Consume costs once at start; power loss pauses progress without reset.

 • Completion unlocks technology and applies explicit effect.

 • Tech branches: hull/depth, battery, tools, cargo, navigation, processing, storage, sensors, station efficiency, automation.

 • Do not grant tech merely because a button was clicked.

 6.9 Communications and sensors
 link_quality = clamp(base_link - depth_penalty - obstruction_penalty + relay_bonus, 0, 1)

 • Low link quality delays/limits noncritical remote commands; local safety rules still run onboard.

 • Scans consume time/power; reveal position, composition confidence, and hazards.

 • Show last contact depth, link quality, telemetry age.

 • Upgrades improve range, relay strength, scan clarity, or confidence.

 6.10 Dock, charge, unload, maintenance
 • Dock states: APPROACHING, DOCKING, DOCKED, UNLOADING, CHARGING, MAINTENANCE, LAUNCH_READY.

 • Cargo transfers only when docked and only up to storage capacity and transfer rate.

 • Charging consumes station power and cannot exceed battery capacity.

 • Repairs consume time and configured components/materials.

 • Launch checks validate hull, battery, tools, mission, and safety; explicit override may allow a warned launch.

 • Dock status is derived from submarine state, not a decorative toggle.

 08. Autonomous Submarine: State Machine and AI
 One small autonomous deep-sea submarine with tiny articulated arms. It scans, grabs, mines, and captures at resource nodes on cliff
 faces and seabed. It is not human-piloted. Local safety rules work even when communications are lost.

       STATE                         BEHAVIOR                                                   EXIT CONDITION

       DOCKED                        Unload, charge, repair, configure                          Launch + checks pass

       PRE_LAUNCH_CHECK              Validate hull, battery, tools, cargo, target               Pass→DEPARTING; fail→DOCKED with
                                                                                                reason

       DEPARTING                     Leave dock safely                                          Clear of dock

       TRAVELING                     Move to waypoint; consume battery                          Target reached→SCANNING

       SCANNING                      Reveal node and hazards                                    Target chosen or scan done

       APPROACHING_NODE              Navigate and align tool                                    Within tool range

       WORKING_NODE                  Mine/grab/capture; energy and wear                         Depleted/full/hazard/complete

       TRANSIT_TO_NEXT               Choose next valid target                                   Reached or return trigger

       RETURNING                     Navigate to dock safely                                    Dock approach

       DOCKING                       Align and connect                                          Docked

       EMERGENCY_RETURN              Abort optional work; prioritize return                     Docked or disabled

       DISABLED                      Cannot safely move/use tool                                Recovery/rescue


 Mission configuration
 • Target: selected node, region, or depth band.

 • Mode: SCAN, MINE, SALVAGE, CAPTURE ORGANICS, MIXED COLLECTION, EXPLORE.

 • Priority: high-value, nearest, safest, player-selected order.

 • Return triggers: cargo threshold, battery reserve, hull threshold, tool condition, mission complete, manual command.

 • Safety reserve, maximum depth, optional maximum mission duration configurable.

 Movement
 distance = sqrt((x_target - x)^2 + (depth_target - depth)^2)

 travel_time = distance / max(effective_speed, minimum_speed)

 effective_speed = base_speed * thruster_condition * load_factor * current_modifier

 Suggested load_factor = max(0.55, 1 - 0.35 * cargo_fraction): full cargo slows the sub by up to 35%.




AI STATION • Extreme Implementation Specification                                                                                  Page 8
 Battery
 energy_used_kWh = total_power_kW * delta_seconds / 3600

 return_reserve = estimated_return_energy * safety_multiplier + emergency_reserve

 Suggested safety multiplier = 1.25. At reserve, stop optional work and enter EMERGENCY_RETURN. This local rule applies even
 without station contact.

 Mining tool
 • Tool has tier, power draw, rate, range, allowed hardness, heat, and condition.

 • Work requires revealed/reachable node, range, alignment, and sufficient tier.

 • Mining decreases node quantity and increases cargo by the same amount, limited by node and capacity.

 • Tool use increases heat/wear; overheating pauses work; low condition reduces rate.

 • Weak tools cannot mine every deposit.
 mining_rate = base_rate * tool_condition_factor * tier_bonus / max(1, hardness)

 mined_amount = min(mining_rate * delta_seconds, node_remaining, cargo_free_capacity)

 Cargo
 cargo_used = sum(quantity_i * mass_per_unit_i)

 cargo_fraction = clamp(cargo_used / cargo_capacity, 0, 1)

 • Suggested return threshold 85%; finish current safe action, then return.

 • At full capacity, stop collection and return.

 • Cargo stays aboard until docking; do not duplicate it in station storage early.

 • If station storage is full, remaining cargo stays aboard and UI shows reason.

 • Bulky salvage and light rare samples may use different mass/volume.

 Autonomous target scoring
 score(node) = value_weight*normalized_value + priority + proximity_bonus - risk_weight*risk -
 energy_weight*estimated_energy

 Filter candidates first: reachable, within depth rating, tool-compatible, not depleted, cargo-compatible, and feasible within battery
 reserve. Choose highest score with deterministic tie-break by node ID. If no valid target, return; never loop on unreachable targets.

 Return and emergency rules
 • Return on cargo threshold, battery reserve, hull threshold, broken tool, mission completion, or explicit order.

 • Resolve immediate collision avoidance before route change.

 • Replan at fixed intervals, not every render frame. Never teleport to dock.

 • If no safe path exists, enter safe holding state, raise alert, try alternate routes.

 • Docking, unloading, charging, and maintenance are separate states with real progress.


 09. Underwater World, Depth, Pressure, Hazards, Deposits
 World structure
 • Vertical side-view environment with stable visible region around sub and scrollable terrain/background.

 • Left/right cliff/reef edges provide ledges and resource attachment points; center water stays open.

 • Seabed has sediment, wrecks, vents, minerals, and unusual samples.

 • Fish/organic sources are limited populations or defined nodes; decorative fish are not automatically collectible.

 • Use seeded placement and reusable tiles; do not create one giant unique level.

 Pressure
 Use depth in meters and seawater approximation rho=1025 kg/m³, g=9.81 m/s², atmospheric pressure=101.3 kPa.




AI STATION • Extreme Implementation Specification                                                                                        Page 9
 pressure_kPa = 101.3 + (1025 * 9.81 * depth_m / 1000)

 pressure_atm = pressure_kPa / 101.3

 At 100 m, pressure is roughly 1,107 kPa absolute. Each sub has rated pressure. Warn when margin is low; block descent beyond rating
 unless a deliberate risk override exists.
 pressure_margin = rated_pressure_kPa / current_pressure_kPa

 overpressure_ratio = max(0, current_pressure / rated_pressure - 1)

 hull_damage_per_s = base_overpressure_damage * overpressure_ratio^2 * stress_multiplier

 The squared model makes small exceedances survivable but large exceedances dangerous. It is a game model, not a real engineering
 certification.

 Temperature, visibility, communications
 visibility = clamp(base_visibility - depth_penalty - turbidity_penalty + sensor_bonus, min_visibility, max_visibility)

 • Low visibility reduces scan radius and target confidence.

 • Temperature modifies battery efficiency/tool cooling/wear only through explicit rules.

 • Show depth, pressure, temperature, visibility, hull, and link quality in sub inspection.

 • Do not change stats without a rule or explainable source.

 Node model
 ResourceNode = { id, x, depth_m, type, composition, remaining_quantity, hardness, hazards, revealed, regeneration_rate
 }

 • Scanning reveals position, composition confidence, and hazards.

 • Mining reduces remaining_quantity; zero means depleted.

 • Renewable nodes recover only if regeneration_rate > 0.

 • Fish populations recover over time only by defined ecology rules.

 • Node contents deterministic for a seed and ID unless an explicit random event is configured.

 Upgrade contract
 Upgrade = { id, cost, prerequisites, target_system, effects:[{field, operation, value}], max_level, install_time_s }

 Every effect names the exact field it changes. Example: Hull Reinforcement Tier 2 increases rated_pressure_kPa by 30%. UI displays
 before/after values.

 Progression gates
 • Deeper zones require hull rating for that pressure range.

 • Hard deposits require sufficient tool tier and power.

 • Advanced recipes require research and correct machine level.

 • Rare samples unlock deep exploration and station resilience tech.

 • Introduce one new constraint at a time, then combine systems later.

 Difficulty
 • Increase constraints, travel cost, resource complexity, visibility, and environmental risk—not arbitrary health multipliers.

 • Early: shallow resources, short missions, simple power and recipes.

 • Mid: power competition, cargo planning, tool tiers, storage bottlenecks, pressure.

 • Late: rare samples, expensive repairs, complex refining, long trips.

 • Events need telegraphing and defined duration/effect.

 Example cascade
 1. Generator condition falls; output declines.

 2. Power allocator protects Core and dock; refinery receives less power.

 3. Refining slows; components arrive later.

 Interaction rules
 • Every action has enabled/disabled/pending/success/failure state.

 14. Save/Load, Determinism, Performance, Mobile
 Save system
 • Save authoritative state: inventory, module conditions/modes/queues, research progress, sub position/state/cargo/battery, node
 depletion, upgrades, alerts, simulation time, settings, RNG state.

 • Use schema_version and migrations. Validate or repair invalid state instead of crashing.

 • Autosave at safe intervals and milestones: research completion, docking, unloading, upgrades.

 • Atomic write: temporary file, validate, replace prior save. Keep last valid backup.

 • Do not serialize transient UI animation as gameplay truth.

 • On load, clamp condition, validate IDs, ensure inventory nonnegative, reconcile jobs.

 Performance
 • Target stable 60 FPS where possible and 30 FPS on lower-end phones.

 • Pool particles/effects; cap bubbles, sparks, fish, debris.

 • Reuse background tiles and parallax layers; no huge unique world image.

 • Keep simulation lightweight; do not recalculate every node each render frame.

 • Animate nearby fish; distant layers can be static/slow.

 • Profile on real mobile hardware early.

 18. Exact Instructions for the AI Game Creator
 Follow these requirements in order. This is an implementation task, not a request to invent a different game.

 1. Inspect current project, engine, code, assets, and existing mechanics before replacing anything. Preserve useful code.

 2. Build composition first: physical station cutaway above, clear waterline, open underwater side-view below, fixed depth meter, small
